1. Disaster recovery and redundancy: Azure Storage redundancy options
=====================================================================

Azure Storage always keeps several copies of your data. The redundancy option you pick for a storage
account decides where those copies live, and therefore which failures the data survives. Redundancy
is set per storage account, so data with different recovery needs belongs in different accounts.

+--------------------+------------------------------------+---------------------+-----------------------+

1.2 Recommendation for AgriStream IoT
-------------------------------------

Critical historical crop harvest records: use RA-GRS (geo-redundant with read access).

  - Harvest records are irreplaceable: they support traceability and export certification, insurance
    claims, bank and audit requirements, and the multi-season yield analysis agronomists use to plan
    crops. They are written once and kept for years, so losing a region's worth of data is not
    acceptable.
  - RA-GRS keeps a second copy hundreds of kilometres away in the paired region, and the farm can
    still read the records from the secondary endpoint while the primary region is down. With South
    Africa North as the primary region the copy stays inside South Africa (South Africa West), which
    helps with POPIA data-residency expectations.
  - Because geo-replication also replicates deletions, add blob versioning, soft delete and an
    immutable (WORM) retention policy so a user mistake or ransomware cannot wipe the records.
  - Older seasons can move to the Cool or Archive tier with a lifecycle management rule. RA-GRS
    supports the Archive tier; ZRS, GZRS and RA-GZRS accounts do not, which is a reason to prefer
    RA-GRS over RA-GZRS here.

Temporary sensor logs: use LRS (locally redundant storage).

  - Raw soil readings arrive every one to two minutes from every probe: very high volume, low value
    per row, and only needed for a short time (dashboards, alerts, daily aggregation). Losing some
    hours of raw logs in a regional disaster does not harm the business; the aggregated results are
    what matter.
  - LRS is the cheapest option and has no geo-replication bandwidth charge, which matters because
    the cost of GRS grows with every write. Three local copies still protect against everyday
    hardware failures.
  - Keep the logs short-lived: a lifecycle rule deletes log blobs after, say, 30 days; for Table
    Storage, write one table per month (or delete old partitions) so expired data can be dropped
    cheaply. If dashboards must keep running through the loss of a single datacenter during harvest
    season, ZRS is the next step up.

Design consequence: AgriStream should use two storage accounts, an RA-GRS "records" account for
harvest records and survey archives and an LRS "telemetry" account for sensor logs, irrigation
events and the command queue, because one account cannot mix redundancy levels. (The practicum build
keeps everything in one account to keep setup simple; the account split is the production design.)


2. Stateless vs stateful architecture
=====================================

A stateless service keeps nothing about a user or a job in its own memory or on its own disk between
requests: every request carries (or can look up) everything it needs, and all lasting data lives in
shared services such as Azure SQL, Blob/Table Storage or a distributed cache. A stateful service
keeps that information on the instance itself, for example in-memory session variables, files saved
to the local disk or a timer running in memory.

2.1 Why App Service and Azure Functions must be stateless to scale horizontally
-------------------------------------------------------------------------------

  - Horizontal scaling (scale-out) adds identical instances behind a load balancer. That only helps
    if ANY instance can serve ANY request. If the user's state is on instance 1, instance 2 cannot
    help with that user.
  - Instances come and go without warning. Autoscale removes instances when CPU or memory drops
    (scale-in), the platform recycles instances for patching and restarts them after deployments,
    and the Functions scale controller creates and destroys Consumption/Flex instances, down to zero
    when idle. Anything kept only on an instance is eventually lost.
  - There is no guarantee that consecutive Function executions run on the same instance: a burst of
    500 queue messages or 200 drone uploads is spread over many instances processing in parallel, so
    a function cannot rely on memory left behind by a previous execution. Each execution must be
    independent, and idempotent because triggers deliver messages at least once.
  - Stateless instances are interchangeable, so a failed instance is simply replaced (better
    reliability) and the platform can balance load evenly (better performance and cost).

2.2 How local session data and local files damage scale-out
-----------------------------------------------------------

  - In-memory session state forces sticky sessions. ASP.NET Core's default session store is in
    memory on each instance, so App Service has to pin each user to the same instance with the ARR
    affinity cookie. When autoscale adds instances during peak daylight hours, existing users stay
    pinned to the instance that is already overloaded; only new users reach the new instances. The
    extra instances sit half idle while the hot instance keeps timing out, so scaling out does not
    relieve the load it was triggered by.
  - Sessions disappear on scale-in or restart. When autoscale removes the instance (or the platform
    recycles it), every session on it is gone: users are logged out and lose half-completed work,
    such as an irrigation schedule or an upload form, in the middle of the working day.
  - Local files are invisible to other instances. A drone image saved to one instance's disk returns
    404 on the other instances, so gallery links break at random depending on which instance
    answers. Local disks are also small, temporary (App Service local and temp storage is wiped on
    restart) and are not backed up. A burst of high-resolution imagery can fill the disk and crash
    the instance.
  - Background work kept in memory, such as a timer that should switch a pump off in 30 minutes, is
    lost when the instance goes, and runs once per instance when there are several (duplicate
    commands).

2.3 How AgriStream IoT stays stateless
--------------------------------------

  - Sign-in uses an encrypted authentication cookie instead of server session; App Service shares
    the ASP.NET Core Data Protection key ring between instances, so any instance can read the
    cookie. ARR affinity can therefore be turned off, letting new instances take load immediately.
  - Drone images and farm media go straight to Azure Blob Storage; sensor telemetry, irrigation
    events and image audits go to Azure Table Storage; users, fields and the master device register
    live in Azure SQL Database.
  - In-memory caching is only a short-lived speed-up (field list 60 s, dashboard snapshot 5-10 s)
    that is safe to lose; the source of truth is always the shared store.
  - The irrigation auto-stop is a delayed message on the Storage Queue, not a timer in memory, so
    whichever instance is alive when it becomes visible processes it. Commands carry a CommandId so
    a retried or duplicated message is applied once (idempotency).
  - The live sensor simulator uses a blob lease so only one web instance writes readings even after
    scale-out, and the X-Served-By response header shows that requests are spread across instances
    during the load test.

When a process genuinely needs state (for example a multi-step harvest workflow), the state is
persisted outside the instance: Durable Functions store orchestration state in Azure Storage, and
session or cache data can go to a distributed cache such as Azure Managed Redis.


3. Serverless triggers and bindings
===================================

have several input and output bindings. They are declared with attributes in the .NET isolated
worker model, and each refers to a connection SETTING name (for example "FarmStorage"), so no

Key takeaway: triggers decide WHEN code runs and drive automatic scaling; input bindings bring data
IN without plumbing code; output bindings send results OUT reliably once the function succeeds.
Together they let each AgriStream function contain only its business logic, which is what makes the
pipeline serverless and easy to scale.
